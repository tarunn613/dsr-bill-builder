# Bill workbook → JSON: agent task prompt

Extraction prompt for the **Excel → PDF** page's JSON import path:

```
built bill .xlsx  →  coding agent (this prompt)  →  JSON  →  app  →  printed PDF
```

The agent (Claude, Antigravity, or similar) reads the workbook **directly** with
openpyxl/exceljs and writes a JSON file. It is not reading pixels — every value comes
out of the cell exactly, so the risk isn't misreading digits, it's misreading
**structure**: which rows are items, which are summary lines, where one measurement
block ends and the next begins.

Only four sheets are in scope — **Schedule, RE, Abstract, Cement**. Everything else in
a real bill (Deviation, AE/EE Test, Recovery registers, Completion Certificate) is
deliberately ignored.

Derived from the real reference bill in `phase-testing/DOC-20260712-WA0000..xlsx`
(9 sheets, 85 items, 75 RE blocks, ~200-row cement template).

---

## Why an agent and not a fixed script

A deterministic parser would need the row offsets to be stable, and they aren't —
these are hand-built workbooks. In the two reference files the same sheet appears as
`Cement` and `Cement `, the abstract is `Abstracrt`, and the header block runs to a
different row in each. An agent adapts to one specific file, and — unlike a vision
model — can **verify its own output by running the arithmetic** before returning it.

That self-check is the reason this approach is worth more than either alternative.

---

## What these bills look like

Structural facts the prompt encodes. Each was verified against the reference
workbook, and each one breaks a naive parse.

**Sheet names are unreliable.** `Abstracrt` (typo), `AE  Test` (double space),
`Cement ` (trailing space). Classify by **column headings**, never by tab name.

**Every sheet repeats the header block — and they disagree.** In the reference,
`Schedule` says agreement `AL-00/EE X-0/DUSIB/2025-26/D-000`, tender ₹12,34567.00,
quoted 00.00% below; `RE` and `Abstracrt` say `AL-00/EEX-0/DUSIB/AE-I/2026-27/D-000`,
tender ₹12,34,567.00, quoted **00.00%** below. A real inconsistency in a real signed
bill. Capture the header **per sheet** — merging them would print one sheet's tender
under another's numbers.

**Category lives in the Ref column.** The Schedule's "Ref to DSR" column holds a DSR
code (`15.2.1`), or `Appd` / `Appd.` / `APPD`, or `Mkt Rate`, or is blank. Copy it
verbatim; do not normalise it into a category field.

**Summary labels carry their own numbers.** `Putting 0.973 factor on total`,
`Add 3.00 % on DSR 2023`, `Less 00.00 % below as pre Contractor quoted rate`. The
label is the record of what was applied — keep the text, don't parse the percentages
out.

**RE has multiple measurement blocks per item.** 75 blocks over 71 distinct S.Nos —
S.No 9 has three, S.No 1 has two. The Abstract then shows one `Qty. B/F from CMB` row
per block plus a `Total` row summing them. Keying blocks by S.No loses data.

**RE's 4th numeric column has no header.** Columns run `Nos | (blank) | Length |
Width | Height/Depth | Quantity`. That unlabelled column is a **multiplier**:
`19 × 1 × 0.93 × 1.1366… × 0.25 = 5.0212`. It is not a serial number.

**A blank RE label means "same as above"** — rows carrying numbers with no label
continue the labelled row above them. Keep the blank.

**Negative Nos = a "less" deduction** (`-1 × 19 × 0.58 × 0.44 × 0.25 = -1.2122`).
The minus sign is load-bearing.

**The Cement sheet is a ~200-row pre-printed template.** Only rows with a quantity are
in use. In a *used* row column A holds the **Schedule's S.No** (`10`, `9`, `17`, `58`,
`APPD`); in an unused row it holds a DSR code (`4.1.2`, `6.13.1`). Column F carries a
`/00` marker meaning the coefficient is per-100 units. `MISCELLANEOUS` and similar are
section headings with no data.

**S.No is signature-critical.** The AE/JE cross-check every line against their BOQ by
serial number before signing. Emit it as a **string**, verbatim, never renumbered or
re-sorted — including merged forms like `16 17`.

**Blank ≠ zero.** An empty qty cell and a printed `0` mean different things (not
measured vs measured as nothing). Emit `null` for blank, `0` for a real zero.

## The gotcha that will bite first

`openpyxl.load_workbook(path, data_only=True)` returns the **cached** result of a
formula — the value Excel computed and stored the last time it saved the file.

- Hand-made bills (like the reference) **have** cached results. Fine.
- Workbooks generated by this app **do not** — every formula cell reads `None`,
  because the file was written by exceljs and never opened in Excel.

So an agent pointed at a fresh app export will silently produce a JSON full of nulls.
The prompt requires the agent to detect this and stop rather than emit an empty bill.

## The prompt

````
Read the bill workbook at <PATH> and write its contents to <OUT>.json.

This is a government construction bill (Delhi DUSIB / DSR format). Read the file
directly with openpyxl (or exceljs) — do NOT transcribe by eye. Write a script,
inspect the sheets, adapt to how THIS file is laid out, and verify your output before
you finish.

=== SCOPE ===

Extract exactly four sheets: schedule, re, abstract, cement.
IGNORE everything else — Deviation, AE Test, EE Test, Recovery registers, Completion
Certificate, and anything else in the workbook.

Identify each sheet by its COLUMN HEADINGS, never by its tab name. Real files have
typos and stray spaces in tab names ("Abstracrt", "Cement ", "AE  Test").

  schedule — a row containing "S.No", "Ref to DSR"/"DSR", "DESCRIPTION", "QTY",
             "UNIT", "RATE", "AMOUNT"
  re       — repeating blocks, each starting at a cell containing
             "Date of Measurement"
  abstract — like schedule but with NO Ref column, and item quantities carried in
             rows containing "Qty. B/F from CMB"
  cement   — a title containing "CEMENT CONSUMPTION", and a coefficient column

=== FIRST: CHECK THE FILE IS READABLE ===

Load with data_only=True and confirm formula cells actually carry cached values.
If most numeric cells come back None, the workbook was written by a tool and never
opened in Excel, so it has no cached results. STOP and report that — do not emit a
JSON full of nulls. (Fix: open the file in Excel/LibreOffice, save, retry.)

=== DO NOT INVENT, DO NOT CORRECT ===

Emit what the cells contain. Never recompute a value to "fix" it, never round, never
reorder rows, never renumber. If the workbook contains an arithmetic error, emit the
wrong value as stored — a downstream check will surface it. Your job is faithful
extraction, not repair.

=== VALUE TYPES ===

  • text  → JSON string, verbatim, including double spaces and typos
  • number → JSON number at FULL stored precision. Do not round. Do not format.
             Do not convert to a string. (A stored 5.0212249999999985 stays
             5.0212249999999985 — the app applies its own display rounding.)
  • blank cell → null
  • a printed 0 → 0        (null and 0 are different: not measured vs measured zero)
  • s_no → ALWAYS a string, even when it is a plain number ("24"), because real
           bills contain merged forms like "16 17"

=== OUTPUT SHAPE ===

{
  "format": "dbill-bill-print",
  "version": 1,
  "source_file": "<filename>",
  "sheets": [ <schedule>, <re>, <abstract>, <cement> ],
  "counts": {
    "schedule_items": 0, "re_blocks": 0, "re_measurement_rows": 0,
    "abstract_items": 0, "cement_items": 0
  },
  "missing_sheets": [],
  "checks": { ... see VERIFY below ... }
}

--- HEADER (every sheet has its own; capture separately, never merge) ---

Sheets in the same workbook legitimately disagree on these — that disagreement is
information, so do not copy one sheet's header onto another.

"header": {
  "bill_title": "",               "Ist & Final Bill" / "Record Entry" /
                                  "CEMENT CONSUMPTION STATEMENT"
  "name_of_work": "",             after "NAME OF WORK:-"
  "sub_head": "",                 after "SUB-HEAD:-"
  "agency": "",                   after "Agency :"
  "agreement_no": "",             the "No:" / "No." reference
  "agreement_date": "",           the "dated:" / "Dated:" value, as printed
  "tender_amount": "",            after "Tender Amount Rs."
  "estimate_amount": "",          after "Estimate Amount Rs."
  "quoted_rate": "",              after "Quoted Rate :", e.g. "00.00% below"
  "date_of_start_agmt": "",
  "date_of_completion_agmt": "",
  "actual_date_of_start": "",
  "actual_date_of_completion": "" may read "Work In Progress" / "WIP"
}

These are often ONE string per row in column A ("Agency : Ram Dass & Sons"), not
label/value pairs. Split on the delimiter and keep the value side, trimmed. Header
lines the sheet does not print → "".

--- SHEET 1: schedule ---

Items run from the row after the column header until the summary block starts. The
summary block is where the label moves into the description column (often merged) and
only an amount follows.

{
  "sheet_type": "schedule",
  "header": { ... },
  "items": [
    { "s_no": "1", "ref": "15.2.1", "description": "<complete cell text>",
      "qty": 8.41, "unit": "Cum", "rate": 2434.25, "amount": 20472.04 }
  ],
  "summary": [
    { "label": "Total Rs.", "amount": 2213284.8200000003 },
    { "label": "Putting 0.973 factor on total", "amount": 2153526.12986 },
    { "label": "Add 3.00  % on DSR 2023", "amount": 64605.78389580001 },
    { "label": "(Rs.)", "amount": 2218131.9137558 },
    { "label": "Less 00.00 % below as pre Contractor quoted rate  Rs.",
      "amount": 574496.1656627522 },
    { "label": "Total Rs.", "amount": 1643635.7480930479 },
    { "label": "Says", "amount": 1643636 }
  ],
  "signatures": ["E.E.", "AE-", "JE"]
}

  • "ref" verbatim — a DSR code, or "Appd"/"Appd."/"Mkt Rate", or "". Do NOT convert
    it to a category.
  • "description" is the full cell text, however long.
  • "summary" = every label/amount line below the last item, IN ORDER, label exactly
    as stored (keep the embedded percentages and any double spaces).
  • An item row with a blank S.No that continues the row above is its own entry with
    "s_no": "".

--- SHEET 2: re (Record Entry / Record of Measurements) ---

A run of repeating BLOCKS. A block starts at a cell containing "Date of Measurement"
and ends after its "Total" row. ONE ITEM CAN OWN SEVERAL BLOCKS — emit each as its
own block, in sheet order, repeating the same s_no. NEVER merge blocks or key them
by s_no.

Columns: S.No | Description | Nos | <unlabelled> | Length | Width | Height/Depth |
Quantity | Unit. The unlabelled 4th numeric column is a MULTIPLIER
(nos × mult × L × W × H = qty) — emit it as "factor", NOT as a serial number.

Within a block:
  • the first row after the column header carries the item's s_no (col A) and its
    description (col B)
  • then measurement rows: label in col B, numbers across
  • a row where the second-to-last column reads "Total" ends the block; its
    Quantity cell is the block total and the next cell is the unit
  • rows containing "C/O" / "MB -" are carry-over notes; "A.E.", "J.E.", "Cont."
    are signature lines — capture the carry-over text, skip the signature row

{
  "sheet_type": "re",
  "header": { ... },
  "blocks": [
    {
      "date_of_measurement": "",
      "page_ref": "P-",
      "s_no": "1",
      "description": "<item description from the block's first row>",
      "rows": [
        { "label": "Gents Section WC (0.92+0.95+0.93)/3 =0.93", "nos": 19,
          "factor": 1, "length": 0.93, "width": 1.1366666666666665,
          "height": 0.24999999999999997, "qty": 5.0212249999999985 },
        { "label": "", "nos": 1, "factor": 20, "length": 0.69, "width": 0.29,
          "height": 0.1, "qty": 0.4002 },
        { "label": "Less WC", "nos": -1, "factor": 19, "length": 0.58,
          "width": 0.44, "height": 0.25, "qty": -1.2122 }
      ],
      "total": 17.79,
      "unit": "Cum",
      "carry_over": "C/O   MB -                               P-"
    }
  ]
}

  • A row with numbers but NO label continues the labelled row above it. Keep
    "label": "" — do not repeat the previous label, do not invent one.
  • Negative "nos" marks a deduction. Keep the sign.
  • Blocks whose rows are all zero still count — emit them as stored.
  • Any of nos/factor/length/width/height may be blank → null.

--- SHEET 3: abstract ---

Columns: S.No | DESCRIPTION | QTY. | UNIT | RATE | AMOUNT (no Ref column).

Each item has one "Qty. B/F from CMB - at P -" row PER RE BLOCK. With more than one,
a "Total" row follows carrying the summed qty, unit, rate and amount. With only one,
that single row carries them itself.

{
  "sheet_type": "abstract",
  "header": { ... },
  "items": [
    { "s_no": "1", "description": "<full text>",
      "bf_rows": [
        { "note": "Qty. B/F from CMB -        at P -", "qty": 17.79 },
        { "note": "Qty. B/F from CMB -        at P -", "qty": 0 }
      ],
      "total_qty": 17.79, "unit": "Cum", "rate": 2434.25,
      "amount": 43305.307499999995 }
  ],
  "summary": [ { "label": "Total Amount (Rs.)", "amount": 2214799.7832999993 } ],
  "recoveries": [
    { "s_no": "1", "label": "Security @ 2.50 % above on Rs.", "base": 1623230,
      "key": "(A)", "amount": 40581 }
  ],
  "recovery_total": { "label": "Total Recoery (A+B+C+D+E)", "amount": 121742 },
  "net_payable":    { "label": "Net Payable Amount Rs.", "amount": 1501488 },
  "certified": ["The Work has been carried out as per Specification & NIT Conditions."],
  "signatures": ["EE C -", "AE-", "JE"]
}

  • Emit a "bf_rows" entry for EVERY B/F line, including qty 0 or blank — their count
    is how many RE blocks the item has.
  • Single-block item: still emit its one bf_row, and repeat the value in "total_qty".
  • Copy recovery labels verbatim, typos included ("Total Recoery").
  • "summary" follows the same rules as the schedule's.

--- SHEET 4: cement ---

Columns: S. No. | Items | Qty | UNIT | Coffiecent as per Unit | <marker> |
Quantity of Cement in Qntl

A ~200-row PRE-PRINTED TEMPLATE — most rows are unused.

  ► Emit a row ONLY if its Qty cell has a value. Skip every template row with a blank
    Qty. Skip section headings ("MISCELLANEOUS") and any row with no coefficient.

In a USED row the first column holds the **Schedule's S.No** ("10", "9", "17", "58")
or "APPD" — NOT a DSR code. Emit whatever is there.

{
  "sheet_type": "cement",
  "header": { ... },
  "items": [
    { "s_no": "10", "item": "C.C. 1:2:4  ( 20 mm nominal size)", "qty": 10.69,
      "unit": "Cum", "coeff": 3.2, "per_marker": "", "cement_qtl": 34.208 }
  ],
  "total_qtl":  { "label": "Total :-", "amount": 135.27913800000002, "unit": "Qntl" },
  "total_bags": { "label": "or", "amount": 270.55827600000003, "unit": "Bags" }
}

  • "per_marker" is the marker column beside the coefficient — "/00" when present
    (the coefficient is per 100 units), otherwise "".
  • "item" is the cement sheet's own short wording ("C.C. 1:2:4", "B/w in
    superstructure C.M 1:6"). Do NOT substitute the Schedule's longer description.

=== VERIFY BEFORE YOU FINISH ===

Run these in code over your OWN output and put the results in "checks". Report
failures — do NOT edit the data to make them pass. A mismatch is a finding about the
workbook, not a bug in your extraction.

  1. schedule: for each item, qty × rate ≈ amount
  2. re: for each row, nos × factor × length × width × height ≈ qty
         (blank factors count as 1 — this is Excel PRODUCT semantics, which skips
         blanks rather than treating them as zero)
  3. re: for each block, Σ row qty ≈ block total
  4. abstract: for each item, Σ bf_rows qty ≈ total_qty, and total_qty × rate ≈ amount
  5. abstract ↔ re: for each s_no, the abstract's bf_rows should match that s_no's RE
     block totals — same count, same values, same order
  6. cement: qty × coeff ≈ cement_qtl (÷100 where per_marker is "/00");
     Σ cement_qtl ≈ total_qtl; total_bags ≈ total_qtl × 2

Use a relative tolerance of 1e-6, or 0.01 absolute on money.

"checks": {
  "schedule_amount": { "checked": 85, "failed": 0, "failures": [] },
  "re_row_qty":      { "checked": 700, "failed": 0, "failures": [] },
  "re_block_total":  { "checked": 75, "failed": 0, "failures": [] },
  "abstract_amount": { "checked": 85, "failed": 0, "failures": [] },
  "abstract_vs_re":  { "checked": 71, "failed": 0, "failures": [] },
  "cement_qtl":      { "checked": 20, "failed": 0, "failures": [] }
}

Each failure: { "s_no": "...", "expected": 0, "found": 0, "note": "" }.

Finally, confirm "counts" matches the actual length of every array you emitted, and
state in your reply: the counts, the check results, and anything about the workbook
that struck you as irregular.
````

## Reading the result

Expected scale for the reference bill, as a sanity check on `counts`:

| | expected |
|---|---|
| schedule items | 85 |
| RE blocks | 75 (71 distinct S.Nos — S.No 9 has 3, S.No 1 has 2) |
| RE measurement rows | ~700 |
| abstract items | 85 |
| cement items | ~20 used rows (of ~200 template rows) |

`checks.abstract_vs_re` is the one that matters most. The Abstract and RE are parsed
independently by different rules, so their agreement is real evidence the block
boundaries were found correctly — the single most likely thing to get wrong.

Genuine failures are expected in check 1 on some bills: these workbooks are hand-built
and do contain arithmetic slips. That is exactly what we want surfaced rather than
silently normalised.
